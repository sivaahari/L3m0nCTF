# SP3 part 3.4: the board, the tick, the programme panel and the flag reply (implementation plan)

> **For agentic workers:** work task by task. Every test is written and **shown failing** before the code that makes it pass. All Python runs inside the platform image (`l3mon/ctfd:dev`) against CTFd's own test helpers (`tools/run-ctfd-tests.sh`, with `L3MON_MOUNT_PLUGINS=1` to test the working tree without a rebuild). A security test is only accepted when it has also been **shown failing with its guard switched off**. Opus audits at the end of the part; it does not build.

**Goal:** a signed-in studio gets, from the real platform, the same answers the approved demo gives: the board (channels, programmes, its own score and place), the tick the pages poll, the extra fields on the programme panel and the extra fields on the reply to a flag. The pages (SP6) are then built against the real server and look the same as in the demo.

**Architecture:** a new plugin `l3mon_board` (it only adds read endpoints and decorates two stock answers; it adds no table). It reads what the earlier parts built: the plan and what is on air (`l3mon_core.airing`, `visibility`), who counts (`counting`), the clock (`clock`), the tick (`tick`), the values (`l3mon_scoring`). The one change to a table: `l3mon_programme` gains `difficulty` and `delivery`, because CTFd has no field for them and the tile and the filters need them. Everything else a programme shows already lives in CTFd (name, category, value, the author in `attribution`, tries in `max_attempts`).

**Tech stack:** Python 3.11 in the CTFd 3.8.8 image, Flask blueprints, Flask-SQLAlchemy 1.4 (CTFd's `db`), freezegun, pytest, a real MariaDB 10.11 for the migration test, node for the golden scenarios (the demo is the reference).

## What probing CTFd 3.8.8 found (2026-10-09)

The probe is `plugins/l3mon_board/tests/probe_facts.py`; `test_board_ctfd_facts.py` keeps the facts that matter as tests, so a CTFd upgrade that changes one fails loudly.

| Fact | Measured | Consequence |
|---|---|---|
| Any challenge route before the start | **403** `{"message": "CTFd has not started yet"}`, the same for a real and a missing id; also the list and the flag attempt | CONFIRM-2 (before): the demo says `phase_closed` with `phase: before`; a small rewrite on the way out gives the contract's shape for a studio that has a team |
| Any challenge route after the end with `view_after_ctf` off | **403** `{"message": "CTFd has ended"}` | the event settings turn `view_after_ctf` on (3.2), so the programmes can be read again after the end |
| A flag after the end with `view_after_ctf` on | **200**, status `correct` for the right flag, **nothing recorded** (0 solves); `incorrect` for a wrong one | CTFd would tell a player after the end whether a flag is right. The demo answers 403 `paused` with `reason: ended`; a guard in front of the attempt gives that and CTFd never sees the flag (CONFIRM-2, ended) |
| A flag while paused | **403** `{"success": true, "data": {"status": "paused", "message": "CTFd is paused"}}` | already the demo's shape; the guard adds `reason: paused` |
| Tries | `Incorrect. You have 1 try remaining.`; the lock-out answers **403** status `ratelimited` "Not accepted. You have 0 tries remaining"; too many wrong flags a minute **429** "You're submitting flags too fast. Try again in N seconds."; a second flag while one is checked **403** `ratelimited` "Another submission is already being processed..." | the client tells these apart by `reason` (`no_tries`, `ratelimited`, `processing`) and `retry_after`; we add them from CTFd's own wording, pinned by a test |
| `Teams.get_place()` and the standings for a studio with no solve, award or hint | `None`; the standings list holds only studios that have scored (or spent) something | the board sends `place: null` for an unranked studio and counts the studios that count (`of`) with its own query |
| A freeze: `get_score()` and `get_place()` for the studio itself | **0 and `None`** for solves after the freeze (CTFd's own view is frozen even for the owner); `get_score(admin=True)` is the live score | the board's own score uses `admin=True`, as the demo ("a studio's own score is always live"), and the place is `null` while frozen |
| `get_solve_counts_for_challenges()` | cached for 60 s, cleared by `clear_challenges()`; honours the freeze for non-admins; counts studios that are not banned or hidden | the board's `solves` uses it (so the freeze is already respected); the plugin's `counted_solve_counts` stays for the crew |
| The challenge answer's keys | `attempts, attribution, category, connection_info, decay, description, files, function, hints, id, initial, logic, max_attempts, minimum, name, next_id, position, rating, ratings, solution_id, solution_state, solved_by_me, solves, state, tags, type, type_data, value, view` | the author is CTFd's `attribution`; we add one key, `l3mon`, and remove nothing |
| An account with no studio (teams mode) | 403 on the challenge routes (CTFd's own refusal) | our endpoints say `no_team` in the contract's envelope |
| Anonymous request with private challenge visibility | **302** to the sign-in page (HTML) | our endpoints answer 401 `auth_required` in JSON |

## Global constraints

- CTFd is pinned at 3.8.8; the plugin refuses to load on any other version.
- Every user-visible score word is **TRP**. The JSON field names stay (`value`, `score`).
- **The board JSON never carries** a flag, a description, hint text, a field called `story`, files, the author, delivery details or attempt limits. A programme the viewer may not see is **absent**: no id, slug, number, name, category, difficulty or value. Counts (`total`, `on_air`, `coming`) are allowed; a channel's storyline is sent only once it has something on air.
- Player endpoints are `GET` only. Answers are `Cache-Control: private, no-cache` (board, with a strong ETag) or `no-store` (ticks). Nothing here writes.
- One request is a small constant number of queries, never one per programme (the speed check is part 3.7; the code is split so a shared cache can be added without changing the answers).
- The unit is TRP, the clock is the event clock, who counts is `counting.py`, what is visible is `visibility.py`. No second copy of any rule.
- A player endpoint answers in the contract's envelope: `{"success": false, "error": "<code>", "message": "...", "request_id": "XXXX-XXXX"}` plus `X-Request-Id`.
- **The freeze is part 3.6.** 3.4 is safe while a freeze is set (the place is null, the solve counts are CTFd's frozen ones, the studio's own score is live) but does not yet freeze the values, hold back the tick for other studios' later solves, or add the studio's own later solves to the counts; each place that needs it goes through one function that 3.6 wraps.

## Decisions made in this part (and why)

1. **`difficulty` and `delivery` become columns of `l3mon_programme`** (a third migration), set through the same `PUT /programmes` call the author kit's sync will use. Alternatives: tags (shown to players, easy to mistype) or a free JSON column (nothing checks it). Both columns have a `CHECK` like every other word the platform stores, and a server default (`medium`, `static_shared`) so a plan loaded without them still works. The author is not a column: CTFd 3.8 already has `attribution`.
2. **The board has two channel numbers**: `id` (the stable row, which programmes point at) and `no` (the number the crew gave it, shown as `CH 03`). The demo had one because its ids were the numbers. Added fields (`no`, `slug`, `picture`, `show_coming`) are allowed; a demo field is never dropped or renamed.
3. **`art` is not sent; `picture` is.** The demo's `art` was a pair of hashed file addresses from the theme build. The plugin does not know the theme's files; the theme maps `picture` (the channel's picture key) to its own.
4. **`ver` is the tick's signature, a string** (counter and phase). The pages compare it for difference only; the contract's "number" is corrected.
5. **`place` is `null` for a studio that has not scored** (CTFd has no row for it), as well as while frozen; `of` counts the studios that count, so "12 of 340" means the same everywhere.
6. **The flag reply is decorated, not replaced.** CTFd's own endpoint keeps judging the flag, recording the solve and valuing the challenge; an `after_request` adds `l3mon` to the answer. Only two things go in front of CTFd: a guard that answers a flag after the end the way the demo does (CTFd would say "correct" and record nothing), and the same wording for "before the start".
7. **`first_blood` is exact**: the studio's solve is the lowest solve id among the studios that count, not "the count was zero a moment ago", so two studios racing for the first solve cannot both be told they were first.
8. **Notifications in the board answer are the public ones for now** (`notif_id`, `notif_ver` from CTFd's notifications). 3.5 adds the studio's private lines and the per-viewer numbering behind the same function (`news.state_for`), so the board is not touched again.
9. **Slugs are not resolved in the API.** The demo let `/api/v1/challenges/<slug>` work for deep links; the theme's page route (SP6) looks the slug up in the board data instead. Resolving a slug inside CTFd's route would put a second lookup in front of the door the release part closed.
10. **Instances are SP4's.** `live` is true for a live delivery; `instance` is `null` until SP4 registers `hooks.instance_summary`. Nothing else about instances is in the board.

## Task 1: programme details (`l3mon_core`, `l3mon_release`)

**Interfaces:** `Programme.difficulty` (`warmup|easy|medium|hard|insane`, default `medium`), `Programme.delivery` (`static_per_participant|static_shared|live_single|live_multi`, default `static_shared`); `PUT /api/v1/l3mon/admin/programmes` accepts `difficulty` and `delivery` per programme (optional; a field that is not sent is not changed), refuses any other word, shows them in the release view.

**Tests:** the model refuses an unknown word (the database does, via `CHECK`); defaults; the plan validates and upserts; an existing programme keeps its values when the call leaves them out; on a real MariaDB the third revision adds exactly these two columns with their `CHECK`s, runs twice and from two workers at once, and downgrades cleanly; a database at the second revision gets them at the next start.

## Task 2: the envelope and the gate (`l3mon_board`)

**Interfaces:** `envelope.ok(data, etag=None, cache="no-store")`, `envelope.fail(code, status, message, **extra)`, `envelope.request_id()`; the decorator `player` (401 `auth_required` when nobody is signed in; 403 `unverified` when the settings ask for a verified email and it is not; 403 `no_team` for a player with no studio; the crew (administrators) pass with no studio).

**Tests:** each refusal's status, code and shape; `X-Request-Id` equals `request_id`; an unexpected error inside a route answers 500 `server_error` with the id and logs the traceback (never in the body).

## Task 3: the board (`l3mon_board`)

**Interfaces:** `board.build(viewer) -> (data, etag)`; `data = {ver, phase: {state, frozen}, team: {id, name, score, place, of} | null, channels: [{id, no, slug, name, synopsis, accent, picture, total, solved, signal, on_air, coming, sponsor: {name, logo} | null}], programmes: [{id, slug, number, channel, order, cell, name, category, difficulty, value, solves, solved_by_me, first_blood_open, live, instance}], notif_id, notif_ver, show_coming}`. Programmes come in channel order, then cell. Before the start: no programmes and every `total` 0. `GET /api/v1/l3mon/board` answers with a strong ETag and `304` on `If-None-Match` (a list, weak forms and `*` included).

**Tests (scenario, in the image):** the numbers of every field for a world with three channels (one sponsored), nine programmes (fixed and dynamic, one withheld, one scheduled, one with an unmet prerequisite), four studios (one banned, one hidden), solves, a hint, a bonus and a void; before the start; paused; ended (every programme listed again); a crew account; the freeze (place null, counts frozen, own score live); the signal and `coming` move as programmes arrive and a pull-back removes a solved tile; the cell keeps its place when others arrive; a studio with no score has `place: null`; the ETag changes when and only when the picture changes (not for the tick, not for another studio's news); a repeated request gives 304; the tick is the plugin's signature.

## Task 4: the tick (`l3mon_board`)

**Interfaces:** `ticks.own(team_id) -> int` (its solves, hint unlocks, awards and private notes plus its voids, in one query), `GET /api/v1/l3mon/ticks` -> `{ver, notif_ver, own}`.

**Tests:** `own` goes up for a solve, a hint, a bonus, a void and a restore; it is 0 for the crew; `ver` moves when a solve is committed and when the phase changes with nothing committed; nothing here depends on who else solved.

## Task 5: the programme panel (`l3mon_board`)

**Interfaces:** `GET /api/v1/challenges/<id>` keeps every stock key and gains `l3mon: {slug, number, channel, channel_name, sponsor, difficulty, author, live, decay, start, floor, first_blood_open, tries_left, score, phase}`. A 403 before the start, for someone who has a studio, becomes the contract's `phase_closed` (`phase: before`).

**Tests:** every field (fixed and dynamic, a decaying standard challenge, limited and unlimited tries under both of CTFd's behaviours, the studio's live score, the phase); a challenge CTFd does not show the viewer gets no block and no new route; the stock keys are untouched; the author is `attribution`; a challenge that is on no channel has no block.

## Task 6: the flag reply (`l3mon_board`)

**Interfaces:** `POST /api/v1/challenges/attempt` keeps CTFd's `{success, data: {status, message}}` and its status codes; `data.l3mon` is added: on `correct` `{value, reel, reels_needed, channel_signal, channel_complete, first_blood, solves}`; on `incorrect` `{tries_left}` when the challenge limits tries; on the 403 and 429 replies `{reason, retry_after?}`. After the end a flag is answered `403 paused` with `reason: ended` before CTFd sees it; before the start the 403 is the contract's `phase_closed`.

**Tests:** each row of the contract's table 4.5 that CTFd can produce; the value after a solve is the value after CTFd's own recalculation; `first_blood` for two studios racing (one only); the counts only include programmes the studio can see; a flag after the end records nothing and tells nothing about the flag (CTFd's `correct` is not reached); a crew account's preview is untouched; the wording of CTFd's tries messages is pinned.

## Task 7: the doors (`l3mon_board`)

**Tests:** with a withheld programme whose name, slug, category and flag contain markers, the board, the ticks, the panel of a visible programme and every flag reply are scanned as the studio, another studio, a visitor and the crew: no marker anywhere (the crew's own admin routes aside); a **control** (the visible programme's markers are present, so the scan cannot pass by being empty); the field `story` is nowhere; the answer for a withheld id on the panel equals the answer for an id that never existed (3.2's test, repeated through the decorated route); the switch-off proof (a board built from every programme fails the scan).

## Task 8: the golden scenarios (`tests/golden`, `private/platform-ui/tools/golden.mjs`)

**What:** the demo is the reference. A neutral made-up world (3 channels, 9 programmes, 4 studios; no event names) is played through the demo step by step (before the start, live, a solve, a hint, a release, a pull-back, a bonus, a void, a restore, paused, ended) and the board and panel answers are written as golden files after ids and times are normalised. `test_golden.py` plays the same steps through CTFd and compares field by field. Differences the demo and CTFd are *meant* to have are listed in the test (channel ids, `ver`, `art`, `registration`, instance details, the notes numbering of 3.5) and nothing else may differ.

## Task 9: the wiring, the whole suite and the record

`tools/verify-image.sh` checks the plugin; `tests/integration/test_board.py` plays the part on the running stack through nginx; `tests/integration/test_hardening.py` gains the new paths; the contract in the private repo (section 9) gets "Built in the CTFd plugin (SP3 part 3.4)"; `docs/deploy/local.md` shows how to read the board; `PROGRESS.md` and the verification log are updated. Rebuild the image. Run: the plugin suite, the real-MariaDB runner (the migration test gains the third revision), CTFd's own 676 with the plugins loaded, the stack recreated, the integration tests, hygiene. Then an independent Opus audit; each finding fixed test first.

## What changed while building (2026-10-09 and 10)

The plan was followed task by task, test first. These things were found by doing the work and are now part of the design:

1. **The loader of the plan refused the author kit's own slugs.** Part 3.2 accepted only lower-case letters, digits and hyphens for a programme's slug; the kit writes `lantern_walk`. The 3.4 test world was the first thing to load a kit-style plan, and it was refused. Programme slugs now also allow underscores (a channel's slug is still hyphens only).
2. **Stock CTFd lets a studio spend TRP on a hint while paused, before the start and after the end**, and says "correct" to a right flag after the end without recording it (so a studio could test its flags after the event). Both are closed by guards, and `test_board_ctfd_facts.py` shows CTFd alone allowing them, so the guards cannot be removed by mistake.
3. **The golden scenarios found two real defects** in the first version of the answers: `first_blood` was false for a hidden studio's own solve (the demo says it is first when no studio that counts was ahead), and CTFd's own `solved_by_me` says false when no studio that counts has solved the challenge, which is wrong for a hidden studio and, under a freeze, for a studio whose only solve came after it. The studio's own record now decides. The scenario also showed that the demo itself leaves a value stale after a ban made after solves (its solve index is rebuilt only when solves change; the contract says so), so the golden script rebuilds it, to compare the real platform with the demo's *intended* behaviour.
4. **`first_blood` under a freeze would have leaked** that another studio solved after the freeze (the earlier solve made it false); it now looks only at solves before the freeze, and the reply counts the studio's own later solve in `solves`.
5. **CTFd dates a solve with the real clock** (the column default is bound at import), so tests that need a solve inside or after a freeze date it themselves.
6. **Mutation checks** (54 deliberate breaks, one at a time, against the plugin's own tests): 47 were caught at once; seven were not and each exposed a test that was too weak (the etag ignoring the news when only an older line was taken away; the crew's `own` counting rows that belong to no studio; the frozen own score; two phase-wording guards that CTFd's own answers make look redundant; tries counted for the captain only; the seconds of a rate limit replaced by a guess). Each got a stronger test, and all seven are caught now.
7. **MariaDB's `CHECK` compares text case-insensitively**, so the database accepts `Live_Single` where the model says `live_single`; the plan loader (exact, in Python) is the gate, as it already was for scoring's function names. The migration test no longer claims otherwise.
8. **Two plugins may not share a test file name** (pytest refuses to collect two `test_ctfd_facts.py`): the board's is `test_board_ctfd_facts.py`.
9. **Not built here, said plainly:** the freeze beyond what the board needs to stay safe (held tick, the studio's own later solves in the counts, values standing still) is part 3.6; the studio's private lines and per-viewer numbering are 3.5; instances are SP4 (`hooks.instance_summary`); slugs in `/api/v1/challenges/<slug>` are the theme's job.
