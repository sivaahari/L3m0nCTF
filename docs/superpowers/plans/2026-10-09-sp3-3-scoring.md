# SP3 part 3.3: scoring (implementation plan)

> **For agentic workers:** work task by task. Every test is written and **shown failing** before the code that makes it pass. All Python runs inside the platform image (`l3mon/ctfd:dev`) against CTFd's own test helpers (`tools/run-ctfd-tests.sh`, with `L3MON_MOUNT_PLUGINS=1` to test the working tree without a rebuild). A security test is only accepted when it has also been **shown failing with its guard switched off**. Opus audits at the end of the part; it does not build.

**Goal:** what a programme is worth stays right whatever happens to the studios that solved it; the crew can set a broken challenge's solves aside and put them back (Revoke, Restore), give a studio TRP with a private message (Bonus), and every studio's private lines are stored where no public route can read them. The hint error says TRP.

**Architecture:** a new plugin `l3mon_scoring` (loaded after `l3mon_release`). It adds no table: the tables `l3mon_void`, `l3mon_bonus`, `l3mon_note` and `l3mon_audit` were built in 3.1 and 3.2. It keeps CTFd's own scoring (a solve is a row in `solves`, TRP is the challenge's current `value`, an award is a row in `awards`, standings are CTFd's) and adds only the missing actions around it. `l3mon_core` gains two shared pieces both plugins now need: the plain-text rule and the lock.

**Tech stack:** Python 3.11 in the CTFd 3.8.8 image, Flask blueprints, Flask-SQLAlchemy 1.4 (CTFd's `db`), freezegun, pytest, a real MariaDB 10.11 and Redis 7 for the concurrency tests, headless Chrome for the page check.

## What probing CTFd 3.8.8 found (2026-10-09)

A four-team world with one dynamic challenge (start 500, floor 200, decay 15), then every admin action that can change who counts, run through the real admin API with the database events recorded. The probe is `plugins/l3mon_scoring/tests/probe_facts.py`; `test_ctfd_facts.py` keeps the facts that matter as tests, so a CTFd upgrade that changes one fails loudly.

| Fact | Measured | Consequence |
|---|---|---|
| Dynamic value after 1, 2, 3, 4 solves | 500, 499, 495, 488 (the logarithmic curve with `n - 1`); every solver is paid the same current value | our formula must match CTFd's to the integer, for both curves, tested over a grid |
| "Mark incorrect" (`PATCH /submissions/<id>`) | deletes the solve **and the submission row** (the design said "keeps it as a Fails row"; wrong). The dynamic value stays stale | nothing remains of how it was solved: this is why Revoke is our own action that keeps the record |
| Ban or hide a team | an ordinary database flush with the `banned` or `hidden` field changed; the value stays stale | note it, and recalculate when the request ends |
| Delete a team, or a solve (admin API) | an ordinary flush with the row deleted; the team's solves go with it; value stale | the same |
| Delete a user | **bulk deletes** (notifications, awards, unlocks, submissions, solves, then the user); no flush; value stale | recalculate when the request ends |
| Core `DELETE` of the `solves` row plus `UPDATE submissions SET type='discard'` | standings, `get_score` and the challenge's solve count drop at once; the submission row stays and loads as a `Discards`; the team can solve again; nothing else is touched | this is how Revoke works; Restore inserts the row back with the same id and date, so the totals and the tie date come back exactly |
| Admin award with `description` empty | a team's total, the standings and the public award list all carry it; the public list shows name, value, category, date and the empty description | the award's name is the only public text |
| Too-dear hint | 400 `{"errors": {"score": "You do not have enough points to unlock this hint"}}` | the only player-facing "points" left in CTFd's API; rewritten to TRP |
| `DELETE` through the test client | 403 without a JSON body (the client adds the CSRF header only when it sends JSON) | test-harness detail; every admin call in our tests sends a body |

## Global constraints

- CTFd is pinned at 3.8.8; the plugin refuses to load on any other version and needs `l3mon_core` (it loads first, by name order).
- Every user-visible score word is **TRP**. Never "points" in text a player can read.
- **Nothing is deleted** by Revoke: the submission stays (as `discard`), the void record keeps who, when, what and why.
- Every admin write is one transaction, writes an audit line (who, what, when, why), clears CTFd's challenge and standings caches, moves the tick (the new rows are watched), and is refused without CTFd's CSRF token and an admin session. No raw SQL built from input.
- Revoke and Restore are safe to send twice and safe to run at once on several workers: a second Revoke finds nothing to set aside and answers 409; the claim on each solve and each void record is a conditional statement whose row count decides who acted.
- A private message (a bonus message, a void reason) is stored in our tables only. The only public text of a bonus is the award's title, "Bonus +50 TRP" or "Adjustment -20 TRP". No public route returns a message or a reason.
- Text from the crew is length-limited and has no control characters and no angle brackets; it is shown as text, never as markup. (Channel names are stricter, because CTFd renders the notification they appear in as markdown; notes and audit lines are shown by our own pages.)
- The platform runs in team mode. In user mode the actions answer 400.
- Dynamic values **stand still while frozen** (the demo's rule, `api-contract.md` section 9): that is part 3.6, which wraps the one function every query asks. 3.3 puts the recalculation behind one function (`values.recalculate`) so 3.6 has one place to wrap.

## Decisions made in this part (and why)

1. **Revoke removes the `solves` row and keeps the submission as `discard`; Restore puts the row back with the same id.** Using CTFd's own "mark incorrect" would destroy the record (measured above). Keeping the id and the date means Restore returns the exact totals and the exact tie-break position. Done with Core statements inside one transaction; the void record is added in the same flush, which also moves the tick.
2. **One function decides a dynamic value.** `values.formula(challenge, n)` is CTFd's curve over a count we supply, so one grouped query values every dynamic challenge. A test compares it with CTFd's own functions for every count from 0 to 80 and both curves, so the two cannot drift.
3. **Hooks notice, the end of the request recalculates, and a safety net catches the rest**: (a) a flush hook notes a ban, a hide, a team, user or solve deleted through the ORM, or a solve added; (b) a bulk-delete hook notes a deleted user or a member removed from a studio (bulk deletes, no flush); both only set a flag on the request, and the value is recalculated when the request ends, **in a fresh transaction after the cause has committed** (never inside it: see "What changed", item 1); (c) Revoke, Restore and the crew's "Recalculate" call it directly; (d) every minute one worker, chosen by an atomic cache add, compares every stored value with its formula, fixes and audits any difference, and logs a warning (the "alert"). The safety net covers what no hook sees (a script, a direct database edit, a race between two players' solves).
4. **The plan lock moves to `l3mon_core`** (`locks.serialize()`), so release control and scoring take the same lock without depending on each other. `reconcile.serialize` stays as a name for it. Revoke and Restore take it, because it is a row no player route touches, and then take **the challenge's own row exclusively, first** (the audit reproduced a deadlock when they took the shared lock through an insert and upgraded it to update the value while CTFd's own update of that value arrived in between; the exclusive lock first makes a player's solve wait a moment instead, and a crew action that loses a lock conflict to a solve already half-way is rolled back and tried again, up to three times). While there is no channel yet, the plan lock falls back to a settings row, because a locking read of an empty table takes only a gap lock and gap locks do not block each other.
5. **A repeated Bonus is refused**, not repeated: the same studio, member, amount and message within a minute answers 409 ("looks like a double click"). Everything else the crew does is idempotent; a Bonus cannot be, and a double award is the one mistake a click can make. A wrong bonus is removed with CTFd's own award delete; the tables cascade.
6. **A team-wide Bonus belongs to the captain's account** (CTFd's team score sums each member's awards by user), and is marked `scope = team`; a Bonus for one member is marked `scope = member`. A bonus given to an account that later leaves the studio, or whose account is deleted, goes with it (CTFd's rule for any award; documented).
7. **Notes are written here and read in 3.5.** This part stores them (Revoke, Restore and Bonus each write one line to the studio) and proves no public route returns one; the player endpoint and the bell come in 3.5 with the other notifications, so the bell is built once.
8. **Deferred, said plainly:** revoking one studio's solve only (the data model allows it; the crew's tool for one cheater is a ban), editing a bonus, and a note for several studios at once.

## Task 1: the shared pieces (`l3mon_core`)

**Interfaces:** `text.UNSAFE_TEXT`, `text.plain_text(value) -> str` (as in 3.2, now here); `text.crew_text(value, limit, required=True) -> (clean, problem|None)` (a string, trimmed, 1 to `limit` characters, no control characters, no `<` or `>`); `locks.serialize()` (commit, then `SELECT ... FOR UPDATE` on the lowest channel); `reconcile.serialize` is the same function.

**Tests:** every existing release test still passes unchanged (the move is invisible); `crew_text` accepts apostrophes, colons, commas, underscores and non-English letters, refuses markup angle brackets and control characters and an empty or over-long text; `serialize` still blocks a second thread on MariaDB (the 3.2 test, unchanged).

## Task 2: values (`l3mon_scoring`)

**Interfaces:** `formula(challenge, solves: int) -> int` (CTFd's `linear` and `logarithmic`, same arithmetic, same ceiling and floor, `decay` 0 read as 1, an unknown function name read as logarithmic, as CTFd does); `recalculate(challenge_ids=None) -> list[(id, old, new)]` (every dynamic challenge by default; one grouped count of counted solves; sets `value` where it differs; clears the challenge and standings caches when anything changed); `drifted() -> list[(id, stored, wanted)]` (read only); `heal(system=True) -> list` (recalculate, and when anything was wrong write one audit line `scoring.heal` and log a warning).

**Tests:** the formula equals CTFd's own `DECAY_FUNCTIONS` for both curves, five starts, floors of 0, 40% and equal to the start, decays of 0, 1, 15 and 50, and every count from 0 to 80 (CTFd's `get_solve_count` is patched to return the count); `recalculate` only touches dynamic challenges, only changes the ones that differ, leaves fixed challenges alone, counts only teams that are neither banned nor hidden, and is repeatable (a second call changes nothing); `heal` audits and logs once, and nothing when nothing was wrong.

## Task 3: the triggers (`l3mon_scoring`)

**Interfaces:** `triggers.install(app)` (once per process): a session `after_flush` hook that notices, while the history of each object still exists, that a Users or Teams row changed `banned` or `hidden` or was deleted, or a Solves row was deleted (every value is then stale), and every solve a flush adds (a player's flag, CTFd's "mark correct", a submission made by hand: only that challenge is stale); an `after_bulk_delete` hook for studios, users, solves and submissions (a deleted user, a member removed from a studio) with the same note; both write only to the request (`flask.g`); an `after_request` function that, when something was noted, rolls back anything a failed view left, recalculates in a fresh transaction, commits (the caches are cleared by the `after_commit` hook) and skips a player's own flag (`/api/v1/challenges/attempt`, which CTFd values itself); a `before_request` function that, once a minute and on one worker (`cache.add` on `l3mon:scoring:checked`), calls `heal`; static and theme requests skip it.

**Tests (scenario, in the image):** four teams solve a dynamic challenge; then, one at a time, each of these leaves the stored value equal to the formula for the counted solves, in the same request: ban, unban, hide, unhide, delete a team, delete a user (the bulk case), delete a solve, "mark incorrect"; a ban of a team that solved nothing changes nothing and writes nothing; a failing recalculation never breaks the request that triggered it (logged); the minute check heals a value changed behind the platform's back, runs once for two calls in a minute, and does not run for static files; the hook does not recurse (a recalculation does not trigger itself). Each trigger is run once with its hook off and must fail.

## Task 4: notes and bonus (`l3mon_scoring`)

**Interfaces:** `notes.tell(team_id, title, text) -> Note` (added to the session, not committed; title up to 100 and text up to 500, clipped); `notes.latest(team_id, limit=5) -> list[{title, content, at}]` newest first. `bonus.give(team_id, user_id=None, trp=0, message="", actor=None) -> dict` validates (a whole number from -1000 to 1000, never 0; a message of 1 to 200 plain characters; the studio exists and is not a user-mode account; the member, if given, belongs to the studio; a studio with no captain and no member given is refused), refuses a repeat inside 60 seconds, then in one transaction creates the award (name "Bonus +50 TRP" or "Adjustment -20 TRP", `description` empty, category `bonus`), the `l3mon_bonus` row, the note (the same title, the message as text) and the audit line `scoring.bonus`.

**Tests:** the studio's CTFd score, its place and the standings move by the amount; a team-wide bonus is on the captain's account with scope `team`, a member's on the member's with scope `member`; the award row has an empty description and the message is only in `l3mon_bonus` and `l3mon_note`; every refusal changes nothing (no award, no bonus, no note, no audit line); a repeat inside a minute is refused and the same bonus after a minute is not; a bonus moves the studio's tie-break date to the award's date (CTFd's rule, pinned); deleting the award through CTFd's own API removes the bonus row and leaves the note; the tick moves once.

## Task 5: Revoke and Restore (`l3mon_scoring`)

**Interfaces:** `voids.revoke(challenge_id, reason) -> dict` and `voids.restore(challenge_id, reason="") -> dict`, both under `locks.serialize()`. **Revoke**: refuses an empty or unsafe reason, an unknown challenge and a challenge nobody has solved (409); for every solve, claims it with a conditional `DELETE` of its `solves` row (row count 1 or skip), sets the submission to `discard`, adds a `Void` (`outcome` open) and tells the studio ("Solve voided", the reason); recalculates the challenge; audits `scoring.revoke` with the count and the value before and after; commits; clears the caches. **Restore**: takes the open records of the challenge in the order they were made; per studio the **earliest** is restored (the solve row goes back with its id, the submission becomes `correct` again, outcome `restored`, `restored_at`, `restored_by`, the studio is told "Solve restored") and the studio's other open records become `superseded`; a studio that holds a solve of the challenge now (it solved again) has all its open records marked `skipped`; a record whose solve cannot come back (its submission or member is gone, the crew changed the submission by hand, or the member holds a solve for another studio) is marked `skipped` and the studio's next record is tried, so a studio keeps a valid solve even when its earliest is gone (with that later solve's own date); recalculates; audits `scoring.restore`. Both answer with counts per outcome.

**Tests (scenario):** revoke then restore returns every studio's total, place and tie-break position exactly (fixed and dynamic, three solvers, with three solvers the dynamic value goes 495 -> 500 -> 495: after a Revoke nobody holds a solve, so it is worth its start value); the revoked studio is told with the reason; nothing is deleted (the submission is `discard`, with its flag text, address and time); a revoked studio can solve again and then Restore marks its old record `skipped` and changes its total by nothing; void, solve again, void again, restore gives the earliest back and `superseded` for the later one; revoke of an unsolved challenge, an empty reason, an unknown id, and a restore with nothing open are refused (409 or 400) with nothing changed; a second Revoke finds nothing; two studios banned or hidden are revoked and restored like any other; a deleted member or studio is skipped, not an error; the audit lines; the tick moves; CTFd's own `get_score` (memoized), `get_standings` and the challenge's solve count agree after each step; every action is refused to a player. **On a real MariaDB:** eight workers revoking one challenge at once produce each void once; a Revoke and a Restore started together end in one consistent state (all revoked or all restored); a worker with a stale view (REPEATABLE READ) still decides from current data.

## What changed while building (2026-10-09)

The plan was followed task by task, test first. These things were found by doing the work and are now part of the design:

1. **The flush hook only notices; the request end recalculates (three versions).** The first version recalculated inside `after_flush`; every test saw the value stay stale, and SQLAlchemy's own warning explained why: changes made to previously clean objects inside `after_flush` are discarded. The second moved the work to `after_flush_postexec` (the commit under way flushes it) and passed every test, and the audit then showed it was wrong for solves: a solve's transaction has inserted a row that points at the challenge (InnoDB takes the shared lock on the challenge row for it), recalculating there asks for the exclusive lock on the same row, and two players doing that at once deadlock, so a player is told 500 and a correct flag is lost (10 of 24 recorded in the audit's probe; CTFd avoids it by valuing the challenge in a second transaction after the commit). The same in-transaction update also made a ban take the challenge row while holding the studio's row, the opposite order to Revoke's. The final version only notes what changed and recalculates when the request ends, in a fresh transaction. The route-level race test could not reproduce the loss in one process (too little overlap), so a deterministic test holds a solve's shared lock open, lets another update queue behind it and commits; it was red against the second version.
2. **CTFd's "mark incorrect" deletes the submission too.** The design said it keeps a `Fails` row; the probe showed both rows gone. That is the reason Revoke exists as our own action, and it is now a test (`test_ctfd_facts.py`) and a corrected row in the design.
3. **Deleting a user is a set of bulk deletes** (notifications, awards, unlocks, submissions, solves, the user) with no flush to hook. The bulk hook sets a flag on the request and the recalculation runs when the request ends.
4. **Losing a race is not an error.** With no channel row to lock (a fresh install, CTFd's own tests) eight simultaneous Restores each reached the "resolved by someone else" tripwire and raised. The data was safe (the unique keys and the conditional updates held) but the loser now steps aside quietly and answers 409; the tripwire remains for the one inconsistent case (a solve put back whose record was taken).
5. **The status line was wiped by every refresh** (found by the first run of the page in a real browser: the success message vanished at once). A refresh no longer touches it.
6. **A bonus cannot be dated by a frozen clock.** CTFd's `Awards.date` column default is bound to the real clock at import, so tie-break tests set the award's date themselves.
7. **Test file names must be unique across plugins** (pytest cannot collect two `test_api.py`); the scoring tests are `test_scoring_api.py` and `test_scoring_doors.py`.
8. **Shared pieces moved to `l3mon_core`** (the plain-text rule, the plan lock, `audit.acting_user`, `audit.recent(prefix=)`), and the browser checks share one Chrome driver (`tests/browser/cdp.mjs`).
9. **The view gained two fields for the page**: `held` (every solve, counted or not, because Revoke sets aside all of them) and the list of studios with their members (names only) for the bonus form.
10. Known and left: a solve by a player at the same instant as a Revoke may or may not be set aside, and the value that results can be one solve out until the next solve or the minute check (stock CTFd has the same race between two players' solves); a team-wide bonus goes with the captain's account if that account is deleted (CTFd's rule for any award).
11. **The independent audit (Opus, 2026-10-09)** read the commit cold and found 2 high, 2 medium, 4 low, with measured scenarios. All eight were checked against the real code first, then fixed test first:
    - **High, a standard challenge with a scoring function was invisible to the plugin.** CTFd 3.8.8 lets any challenge decay (`function` Linear or Logarithmic in the editor, read from the challenge's own `initial`, `minimum`, `decay` columns), not only the `dynamic` type. Ban, Revoke and the minute check all missed it and the crew's page called it "fixed". `values.decaying_rows` now takes both kinds; the view calls both "dynamic". Tests: values, trigger, void and API layers.
    - **High, caches left stale when the value did not move.** Revoke and Restore cleared CTFd's caches only through a changed value; a fixed challenge (or a dynamic one with one solver) left the board, the studio's score and the challenge list old for up to five minutes while the tick told clients to refetch at once. They now mark the transaction whenever a solve is deleted or put back. The older test helpers cleared the caches by hand before reading, which is why nothing saw it; `test_scoring_caches.py` warms the caches through player requests and reads them again without clearing anything.
    - **Medium, a deadlock with CTFd's own value update** (see decision 4; reproduced on MariaDB, now a test that fails without the fix).
    - **Medium, other crew actions the triggers missed:** CTFd's "mark correct", a correct submission made by hand, and removing a member who had solved (a bulk delete of submissions). The flush hook now also notes added solves; the bulk hook also watches submissions. A false "drift" alarm no longer fires on a routine crew action.
    - **Low, the plan lock did nothing while no channel existed** (eight simultaneous bonuses were all given). It falls back to a settings row. The first version of the fix reintroduced a stale read view (the row was found with a plain read before the lock was won); the 8-worker test on MariaDB caught it, and the lookup now ends its own transaction first.
    - **Low, the Restore confirmation did not show the line the studios will read.** It does, and a Revoke of a programme that is still visible to players warns that a studio could solve it again at once (and says to withhold it first).
    - **Low, `crew_text` let through characters that reorder or hide text** (C1 controls, line and paragraph separators, direction marks, the zero-width space, the byte-order mark). Refused; the zero-width joiner and non-joiner stay, because Malayalam, Kannada, Tamil, Hindi and emoji sequences need them.
    - **Low, `after_commit` also fires when a savepoint is released** (SQLAlchemy 1.4). Harmless today by the order the code runs in; both the cache hook and the core tick now wait for the real commit.
