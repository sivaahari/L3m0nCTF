# SP3 part 3.6: the scoreboard freeze (implementation plan)

> **For agentic workers:** build test first, one task at a time, with the mutation checks and the independent review of the verification section. Steps use checkboxes.

**Goal:** while the scoreboard is frozen, nothing a studio can read shows that another studio solved: no count, no value, no rank, no score, no tick, no tag of any answer. A studio always sees its own solves. Lifting the freeze puts everything right in the same request.

**Architecture:** the freeze is CTFd's own single time (`freeze` setting, no second switch). CTFd already leaves solves and awards dated at or after it out of the public lists; what it does not do is keep a dynamic challenge's *value* still, and the public standings are made from the current stored values. So the platform keeps the stored values still: while frozen, **nothing writes `challenges.value`**. Every surface (our endpoints, CTFd's own pages, a studio's own live score) then reads the same still numbers, and none of them needs to know about the freeze. The shared tick ignores solves while frozen; the per-viewer solve counts add a studio's own later solves; the final CTFtime feed waits for the freeze to be lifted.

**Tech stack:** CTFd 3.8.8 plugin API (functions wrapped at load), SQLAlchemy 1.4 events, MariaDB row locks, pytest in the CTFd image; the golden scenarios come from the approved demo.

## Global constraints

- The freeze is the `freeze` setting and nothing else. It is **not** in the locked event settings (`config/event.toml` renders CTFd's preset, which the admin page cannot change): the crew sets it, moves it and lifts it from CTFd's admin page or API during the round.
- A studio's own solves, score and place are never hidden from it, except that its place is `null` while frozen (the page says "Ranks frozen").
- Nothing here may make a normal (not frozen) round slower or different: every new check is one cached setting read.
- A programme's true value is a function of the solves; the solves are never touched, so a value that was held can always be put right.

## What the demo does while frozen (the reference, `private/platform-ui/server/world.mjs`, `solves.mjs`, `api-board.mjs`)

| Rule | The demo |
|---|---|
| The public ranking | kept as a picture taken at the freeze (`world.frozen`) |
| A studio's place | `null`, "Ranks frozen" |
| A studio's own score | live |
| Dynamic values | captured at the freeze (`world.frozenValues`) and used by everything until it ends |
| Solve counts | the count at the freeze, plus the viewer's own later solve (never for a hidden or suspended studio) |
| The tick | a solve made while frozen does not move it |
| Revoke and Restore | the live numbers change at once; the public counts follow for solves from before the freeze |

## Measured in CTFd 3.8.8 (kept as tests in `plugins/l3mon_scoring/tests/test_freeze_facts.py`)

| Fact | Consequence |
|---|---|
| The public standings, solve counts and a team's public score leave out every solve and award dated at or after `freeze`; the owner's view (`admin=True`) and the crew ignore it | CTFd already hides the solves; the standings and counts need nothing from us |
| The public standings are made from the challenges' **current stored values**: a value that falls after the freeze moves a frozen score | The leak. Keeping the stored values still closes it everywhere at once |
| The freeze stays applied after the end of the event until somebody unsets it | "Frozen" is the clock's test (freeze set and now at or after it), not tied to the end |
| After a player's flag CTFd values the challenge in **two** places: the module function `CTFd.plugins.challenges.calculate_value` (the base class calls it for every challenge that carries a scoring function, the dynamic type included) and the dynamic type's own classmethod, so a dynamic challenge is valued twice per solve; both also run on create and update | Two functions to wrap |
| CTFd's update sets the crew's edits and relies on `calculate_value` to commit them | The wrapper must commit when it holds, or an edit made during the freeze is lost |
| On MariaDB (REPEATABLE READ) a read view begun earlier in the transaction hides what another transaction commits while we wait for a row lock | The wrapper ends the transaction before its locking read (found by the MariaDB test; SQLite cannot show it) |

## Decisions

1. **Keep the stored values still instead of a snapshot read.** A read-side snapshot would have to override every reader of `challenges.value`, including CTFd's own pages. Holding the write makes every reader right without knowing. The cost is that the stored values are stale until the freeze is lifted, which is handled by decisions 3 to 5.
2. **"Frozen" is `current_phase().frozen`**: a freeze is set and now is at or after it. It does not depend on the end of the event.
3. **Two wrappers on CTFd's valuation functions** (`freeze.py`, installed at load). While frozen they commit what is pending (the crew's edits) and return without writing the value. Otherwise they end the transaction, take the challenge row's lock as the first statement and only then let CTFd count: the race left open by part 3.3's audit (CTFd counts, a Revoke commits, CTFd writes the old count) is closed in the same place. (Changed after the review: a challenge that has no value yet is given its start value, see the review section.)
4. **Our own writers hold too**: `values.recalculate`, `heal` and `drifted` do nothing while frozen. Revoke and Restore therefore leave the value alone during the freeze.
5. **Lifting is noticed by a trigger on the `freeze` setting** (a flush that sets, changes or removes it): the request that does it recalculates every value when it ends. Moving the freeze to a later time lifts it too. The minute check is the last resort. (Changed after the review: setting or moving the freeze values each challenge as of the freeze time, and a lift made outside a request is noticed by the next request.)
6. **The crew's page and API** say `frozen: true`, show "held; it becomes N TRP", disable "Recalculate values", and the recalculate call answers 409.
7. **The tick ignores solves while frozen** (new, set aside, put back; one by one or in bulk); every other change still moves it, and a failure to read the phase never hides a change. The solver's own page follows its own number (`own`), and the signature's phase part changes at the freeze and when it is lifted. (Changed after the review: only solves dated at or after the freeze.)
8. **Counts per viewer** (`l3mon_board/counts.py`): CTFd's count (the frozen one) plus the viewer's own solves at or after the freeze, only for a studio that counts. The board, the panel, the Guide's story meter and the flag reply all use it, so they say the same number.
9. **The public list is made from the data, not kept as a picture.** This differs from the demo on purpose: a Revoke, a Restore, a ban or a hide of something that happened *before* the freeze shows on the public list at once, so a banned cheater leaves it and voided TRP comes off it, while nothing about solves *after* the freeze can show. The golden scenarios therefore ask no scoreboard right after the void during the freeze, and `test_freeze_board.py` pins the behaviour.
10. **The final CTFtime feed waits for the freeze to be lifted** (404 with a plain message): its totals come from the stored values, which are held while the freeze lasts. Lifting puts them right.
11. **Accepted and said plainly:** a hint bought during the freeze moves the shared tick (it tells that somebody bought a hint, not that anybody solved; the demo does the same). Anything the crew writes during the freeze (a bonus) is dated after it and so is not on the public list until the lift.
12. **Left to 3.7:** the speed check and the decision whether CTFd's database connection should run at READ COMMITTED (it would remove the cause of the stale-read finding at its root).

## Tasks

1. **Facts as tests** (`test_freeze_facts.py`).
2. **The hold** (`freeze.py`, `values.py`): the two wrappers, recalculate, heal and drifted; a flag while frozen, a standard challenge with a scoring function, the crew's edit, a fixed challenge, own score.
3. **Lifting** (`triggers.py`): the crew's own call, moving the freeze later, the trigger switched off and the minute check as the last resort.
4. **The crew's page and API** (`api.py`, `scoring.js`).
5. **The lock on MariaDB** (`test_freeze_mariadb.py`): locked and unlocked, so the race is shown real.
6. **The tick** (`tick.py`).
7. **Counts** (`counts.py`) and the board, panel, Guide and reply that use it.
8. **The final feed** (`l3mon_ctftime`).
9. **Golden scenarios**: a fifth studio, six freeze steps, the harness teaching the real platform the freeze and dating its rows on the scenario's clock.
10. **The leak scan**: a byte-for-byte comparison of everything a studio can read before and after other studios solve; lifting catches everything up.
11. **Mutation checks, the independent review, the stack run, the records** (contract section 13, `docs/deploy/local.md`, PROGRESS, the verification log).

## The independent review and what changed (2026-10-15)

A second model reviewed a frozen copy of the part (60 endpoints compared byte for byte before and after other studios solved, real MariaDB 10.11 concurrency, CTFd's own
challenge tests with the wrappers forced on). It found **no high finding, 3 medium, 4 low and 6 notes**. The core held: values stood still, nothing a studio reads moved, and
the locking and the lift were correct under eight simultaneous flags, a lift racing six late solves, and a lift while a Revoke held the row. Each finding below was reproduced
as a failing test first (`test_freeze_review.py` and additions to `test_tick.py` and `test_freeze_board.py`), then fixed, then broken on purpose.

| # | Finding | Fix |
|---|---|---|
| M1 | A freeze set to a time already past held whatever value was stored at that moment, made from solves the freeze hides: with alpha and bravo solved two hours ago and charlie ten minutes ago, a freeze at "30 minutes ago" left the value at the three-studio number while the public list showed two studios | The values are worked out **as of the freeze time** when the freeze is set or moved: `values.recalculate(as_of_freeze=True)` counts only the studios that solved before the freeze (`counting.counted_solve_counts(before=)`), in the request that sets it. A freeze in the future changes nothing; a lift counts everything again. Revoke, a ban and the minute check still leave the held values alone, as in the demo |
| M2 | CTFd's challenge ratings are public totals and only a solver may rate: a rating after a solve made after the freeze told everybody that somebody solved (the programme panel passes the totals on) | **Nobody but the crew rates while the scoreboard is frozen** (`freeze._ratings_door`, a 403 with a plain message); reading ratings is not closed. The totals therefore stand still too |
| M3 | The tick ignored every solve while frozen, so the crew's own routes (mark a pre-freeze submission correct or incorrect, delete a pre-freeze solve) changed the public list and left the open pages stale | Only solves **dated at or after the freeze** are held back; a solve from before it moves the tick. A date that is not at hand (a deleted row never loaded) counts as before: moving the tick once too often is harmless. Bulk changes stay held back (the rows cannot be seen) |
| L1 | A held value could disagree with the public count without leaking (a freeze moved later but still in the past; a solve dated before the freeze but valued after it) | The first half is fixed with M1. The second (a solve at the very second of the freeze) is accepted: both numbers are from before the freeze and nothing later shows |
| L2 | A lift made outside a request (a script, the shell) was only found by the minute check | `triggers._watch_for_a_lift`: the next request that finds the scoreboard no longer frozen, where this process saw it frozen, puts every value right when it ends |
| L3 | A standard challenge with a scoring function, created during the freeze without `value`, kept NULL until the lift | The held valuation gives a missing value its start value (`values.start_value`) |
| L4 | The programme panel turned CTFd's `solves: null` (scores hidden) into a number and an open first blood | A hidden count stays hidden |
| N1 | (From part 3.3, found here) the minute check took the challenge rows' locks and kept them to the end of the request when it had nothing to fix, so other players' flags waited on it | `heal()` ends its transaction when nothing changed |

Accepted and recorded, not changed: **N2** a hint bought by another studio moves the tick during the freeze (point 11 above, the demo does the same); **N3** CTFd's own challenge
list and the panel's rendered HTML still give the frozen count without the studio's own late solve, so rule 2 holds on our keys only; **N4** during the freeze the crew's own
`admin=True` standings also use the held values, so the crew does not see the true totals until the lift (the crew page says "held; it becomes N TRP"); **N5** a stale
configuration read in a worker whose database read view began before the lift (the window is milliseconds and was not reproduced); **N6** a future challenge type (SP4) that
values itself bypasses the hold: the facts test pins only CTFd's two functions, and SP4 must wrap its own.
